# devdeck requirements

The source of truth for what devdeck must do. Every requirement has an id so plans,
tests and commits can point at it. When a requirement changes, edit it here first.

Status markers: `[ ]` not started · `[~]` partly done · `[x]` done and tested.

## 1. Product

- [~] **R1.1** Native desktop app written in Rust, shipped as a single executable.
- [ ] **R1.2** Linux first (Wayland and X11); macOS 15 and later on Apple silicon, built from source (decided 2026-11-10, `docs/plans/macos.md`). Wide desktop screens (1920×1080 and up). No mobile or narrow layouts.
- [~] **R1.3** As fast as possible and as cheap as possible: GPU-rendered text, near-zero CPU when idle, minimal RAM. Only visible content is drawn; long lists and logs are virtualized.
- [~] **R1.4** Self-contained. No dependency on the author's own scripts or tools (`cs`, `f`, the project daemon, aliases). External programs (pnpm, go, kubectl, docker…) are optional capabilities, detected at runtime.
- [~] **R1.5** Shareable. Nothing about one machine is hard-coded: paths, envs, clusters, kubeconfigs, folders and tools all come from config.
- [~] **R1.6** Monospace font everywhere.

## 2. Workspaces

- [~] **R2.1** The app holds several workspaces (for example "work" and "personal"). They share nothing: folders, envs, cluster settings, layouts, pins, processes, history. The theme and the UI scale are global (decided 2026-11-07).
- [x] **R2.2** Exactly one workspace is displayed at a time. Switching does not stop anything: the others keep running in the background and come back in their exact state.
- [~] **R2.3** Envs and cluster access are optional per workspace. When a workspace has none, the related UI (env selector, Cluster area, deploy actions) does not appear at all.

## 3. Layout engine (panes, tabs, windows)

- [~] **R3.1** The window body is one tree of splits. Every leaf is a pane. There are no special docks: any pane can sit anywhere.
- [~] **R3.2** A pane is a generic container of tabs. A tab shows exactly one view. Any view type can open in any pane.
- [~] **R3.3** Views are implemented once and registered natively (examples: command output, app details, service inspector, pod, logs, file, note, branch matrix, ports). Adding a view type must not require touching the layout engine.
- [~] **R3.4** Tabs move by drag and drop: into another pane's tab strip or header, onto a pane's edge to split it, or beside a whole column or row (R3.13). Panes move the same way (drag the pane by the handle of its tab strip or header).
- [~] **R3.5** Dividers are resizable by dragging.
- [~] **R3.6** A pane can collapse to only its tab strip (or header), giving its space to its neighbours. Clicking a tab (or a key) expands it again.
- [~] **R3.7** A pane can be maximized and restored.
- [~] **R3.8** A tab can be detached into its own OS window. That window contains a single pane (it can receive more tabs), nothing else of the app. It is owned by the main process: closing the main app closes it. The detached window's title bar has a re-attach button (⇲) next to close (×): ⇲ sends its tabs back to the main window, × closes the window and its tabs. Dragging tabs between windows is not required (decided 2026-11-07: GPUI can't do it on Wayland; "Send to…" covers it).
- [x] **R3.11** "Send to…" on a tab and on a pane (menu, pane button, key): every pane of every window shows a number and is listed by its active tab and position, plus "new window". Pick by number key, by clicking the list, or by clicking the pane. Esc cancels. Sending a pane moves all its tabs.
- [~] **R3.9** Panes never overlap. Each pane clips its own content; content wider than the pane scrolls inside it.
- [x] **R3.10** Named layouts per workspace: save the current arrangement, switch between layouts.
- [x] **R3.12** A pane with one tab, or none, shows a header instead of a tab strip (decided 2026-11-08, user): the same height and place, so bodies stay aligned and nothing jumps when a second tab comes or goes. It names the view (no tab shape) and holds the pane's buttons, then × at its far right, which closes the tab. Its title is the tab: drag, double-click to maximize, middle-click to close, right-click for the tab's menu. Focus is a line across the whole header. A tab dropped on it joins the pane, which then shows its tab strip. An empty pane's header has no title and its menu is the pane's.
- [~] **R3.13** A dragged tab, pane, list row or file lands beside a pane or beside any column or row its edge belongs to, up to the whole window, taking half of it: two stacked panes and a tab dropped at the window's right edge give a full-height column on the right in one drop. While dragging, the highlight is the exact rectangle it will take. The same by keyboard: "move tab to window edge" (decided 2026-11-08, user).
- [x] **R3.14** A tab shows an icon saying what kind of view it is, then a short name saying which one, like a browser's tab (user, 2026-11-09): a terminal by its folder (no "terminal ·"), a run by its app and command (its icon green running, amber stopping, red failed), a service, its logs or a pod by name and env (a protected env in red), a note by its name, a file by its name (a code file's own icon). Its full title is its tooltip. The same in a one-tab header; a collapsed pane's rail shows the icons.

## 4. Lists and text

- [~] **R4.1** Every list is sorted alphabetically. Exception: the git panel's branches, newest first (user, 2026-11-09).
- [x] **R4.2** Lists have two sections, Pinned and All, both alphabetical. Pin or unpin with a menu action, a key, or by dragging a row between sections. Lists inside a view (an app's commands, its notes) are one alphabetical list.
- [~] **R4.6** The Apps list's All section is a tree that keeps the folders apps sit in (a monorepo holds its apps and packages). Rows are closed at first and say what they hold (how many, something running, a missing tool); → and ← open and close, as do the chevron and a double click on a folder. What's open is remembered per workspace. A filter or "running only" shows the matches with their folders open, and leaves what's open as it was. Pinned stays flat. (Decided 2026-11-07.)
- [~] **R4.3** No automatic "mine" grouping and no recency-ordered sections (groups the user makes are R4.8). Running state is shown as an indicator on the row, with a "running only" filter.
- [~] **R4.4** Text never wraps unless a view explicitly allows it (for example a log view with wrapping toggled on). Single-line text truncates with an ellipsis (end or middle truncation) and shows the full text on hover. Terminals (run output, shell tabs) wrap at the pane width and never scroll horizontally (decided 2026-11-07).
- [~] **R4.5** Status markers and glyphs never shrink or move to another line; the label truncates instead.
- [~] **R4.7** Pinned and All fold from their header, which keeps its count. What's folded is remembered per workspace and list. A filter or "running only" shows the matches of a folded section and leaves what's folded as it was. (Decided 2026-11-08.)
- [~] **R4.8** The user makes groups in All: nested, folded and opened like folders, remembered, first at each level, alphabetical. Every list but Terminals; Cluster groups are shared by every env. Not in Terminals or Notes (user, 2026-11-09: notes stay with their project). Made from the All header's menu or a group's, renamed, deleted (what it holds moves to its parent: nothing is lost). An item, or a folder of the Apps tree with all it holds, moves in by a drop on the group (on the All header: back to the top) or "Move to group ▸". A pinned item keeps its group and goes back to it when unpinned; dropped on a group it is unpinned into it, on the All header unpinned to the top. Something inside a folder put in a group can be taken back to the top on its own. (Decided 2026-11-08.)
- [~] **R4.9** The sidebar's right edge drags its width, kept between 200 px and half the window; a double click goes back to the default. One width for the app, remembered. (Decided 2026-11-08.)

## 5. Interaction

- [~] **R5.1** Every action works with both mouse and keyboard. Actions are registered once (id, label, default key, availability with a reason) and reused by buttons, context menus, the palette and shortcuts. On macOS, an app key written ctrl+… in these requirements is cmd+… (`docs/PLATFORMS.md` L10).
- [~] **R5.2** Right-click opens a context menu on every interactive element (rows, tabs, panes, commands, pods).
- [~] **R5.3** Command palette (ctrl+k) with fuzzy search over apps, commands, deployments, envs, layouts, workspaces and actions. `@35` picks the env for one run. Tab shows an app's commands.
- [~] **R5.4** k9s-inspired single-key shortcuts. Shortcuts are not shown in the UI (no key hints in menus, tooltips, labels or a hint bar: it clutters); they are listed on one page, today the searchable cheat sheet (`?`, ctrl+/), to be redesigned later (changed 2026-11-07, user decision).
- [~] **R5.5** Unavailable actions show why (missing tool, protected env, no permission). In a menu an unavailable item is only dimmed, without its reason (user, 2026-11-10: the reason widened the menu, R9.10).
- [ ] **R5.6** Edit mode (user, 2026-11-08): potentially destructive actions (deploys, a replace push, a git abort, stopping a process devdeck didn't start, a shell in a pod) run only while edit mode is on: a title bar button, turned on after a modal saying what it allows, off without one, off at every start. devdeck never pushes `main` or `master`, edit mode or not.
- [~] **R5.7** A right-click menu (user, 2026-11-08): what a view offers there, then every action that can take what was right-clicked, shown only where it applies. Content: text selected in a terminal (a run's output or a shell), a file or a note (source or rendered; 2026-11-08, user); first actions: Copy and **Share with**, which pastes the text as it is (no Enter) into another terminal of the workspace whose program takes pastes safely (bracketed paste; others listed, refused with why) and shows it; its own click goes where text went last. Later content: images opened. The menu key opens it at the selection (at the caret in a file or a note), else the tab's menu. Terminals are named by their folder's last part everywhere (tabs, lists, menus).
- [~] **R5.8** A menu stays open when one of its toggles (on or off: "show the time") is used, by mouse or keyboard, so several can be changed in a row; picking one of several, or an action, closes it (user, 2026-11-10).

## 6. Local apps

- [x] **R6.1** Apps are discovered automatically from the workspace's folders: `package.json` scripts, pnpm/npm workspaces (monorepo packages), Taskfile tasks, Makefile targets, docker compose files, `.vscode/launch.json`, Go modules with a main package, Cargo projects (one run command per binary when `cargo run` alone can't choose). A folder that isn't a project is looked into for projects, down to three levels under the workspace folder (decided 2026-11-07). New folders appear without configuration.
- [x] **R6.2** Runnable apps and libraries are told apart; libraries stay listed but de-emphasized.
- [~] **R6.3** Commands have tiers: primary (start, dev, serve…), secondary (build, test, codegen…), hidden (lint, format, prepare, pre/post hooks…). Hidden ones stay reachable.
- [x] **R6.4** Overrides (names, commands, env binding, ports, URLs, hidden apps) live only in the central config, never in the project folders.
- [~] **R6.5** Each command declares the tools it needs. When one is missing, the app and its commands show as disabled with a warning sign and the missing thing named ("go not found", ".nvmrc wants node 20, which isn't installed"). A script's programs that the project's install provides are checked too ("vite isn't installed: run npm install"), and Node projects get an install command (decided 2026-11-07).
- [~] **R6.6** Env for a run: a workspace-wide default plus a per-app override. How the env is applied is generic and declared: command argument (preferred: nothing written to disk; a `{env}` placeholder in the command line), environment variable, rewrite of a gitignored file, or none. Bindings are added per app as needed. The UI says how it is applied.
- [~] **R6.7** Commands run in a pseudo-terminal: colors, progress output and exit codes are real. Several run at once. Stop, restart, run again, exit status, crash notification. A run that ends on its own with code 0 shows a green ✓, "succeeded in 14 s", and a toast (decided 2026-11-07). Links in the output (`http`, `https`, `file`, and those programs mark) are underlined while shift is held over it; shift+click opens one in the browser (decided 2026-11-07).
- [x] **R6.8** Node version per project from `.nvmrc`, resolved against configured node installations. Without an `.nvmrc`, `engines.node` in `package.json`: the default Node when it fits, else the newest installed one that does (decided 2026-11-07).
- [~] **R6.9** Listening ports are detected per run. Port conflicts are reported before starting, with an option to stop the holder.
- [~] **R6.12** Terminal tabs: the user's shell in a folder (the focused tab's app folder, else the workspace's first folder), on the run tab's terminal; `ctrl+shift+t` opens one. A terminal's shell lives apart from its tabs, which are views on it: the same terminal can show in several layouts, and closing a tab, the detached window holding it or a layout, or switching layouts, never ends the shell (a process it runs keeps its port). Every terminal of a workspace is listed in the sidebar's Terminals view (`ctrl+5`), running or not (one a layout shows that hasn't started since a restart: "not started"): its folder, what runs in it, where it shows (here, other layouts, nowhere); **Open** re-attaches it here (the same shell, or starts it), **Stop** ends its shell (its tabs stay, showing it ended; ⏎ starts it again). A terminal whose shell isn't running and that no tab shows is forgotten. Quitting asks while a shell runs something (decided 2026-11-07; tabs as views, 2026-11-08).
- [~] **R6.13** Opening something somewhere: "Open terminal here" on a tab, a pane and an app row opens a shell in that folder at its default place (this pane; the focused one for an app row); resting on it 300 ms, or →, shows every place ("Send to…"'s panes and a new window) to pick another. The Terminals list's "Open" offers the same places. Any later "open …" item works this way (decided 2026-11-07).
- [~] **R6.11** A command takes arguments without becoming another command: in its run tab, recent arguments (per workspace, app and command), none, or new ones typed; choosing them starts or restarts the run. Each toolchain adds them its way (npm and `cargo run` after `--`). Restart and reopen keep them (decided 2026-11-07).
- [ ] **R6.10** A git panel per app and service (changed 2026-11-08, user decision, M3): the repository's state (branch, upstream, ahead/behind, changes), its local and remote branches with their last commit and the envs running them (image tags are branch names), newest first, remote ones only on demand (a button and a key; user, 2026-11-09), each row's message and name cut so its author and age always show; switch branch, fetch, pull (fast-forward only), create a branch, push (publish, plain, or replacing a rewritten branch only when nothing on the remote is lost; never a force push that loses anything), each confirmed in plain words, but a switch only when tracked files have uncommitted changes, which it lists (user, 2026-11-09), and a push only when it replaces the remote's branch (user, 2026-11-10). An operation under way (rebase, merge…) is shown and blocks every write but its abort. No commit, merge, rebase, stash or editor features; worktrees are a later idea.

## 7. Cluster (optional per workspace)

- [~] **R7.1** Per env: list of deployments (alphabetical, Pinned and All) with status, image tag, ready count, restarts, running since. The Cluster list has its own env (user, 2026-11-09): a dropdown whose first choice syncs it with the workspace's env (the default, following it), the others show another env's deployments without changing the workspace's (the one runs use); a service opens in the list's env.
- [~] **R7.2** Service inspector: header and actions; live CPU and memory against request and limit; pods (status, ready, restarts, last termination reason, age, node, cpu, memory); container (image, ports, resources, configmap); deploy history recorded by devdeck.
- [~] **R7.3** Image tag editor with suggestions (tags deployed on other envs, devdeck history, free text), an unsaved marker, save with ctrl+s or a button, and a confirmation that states the exact change and the exact command.
- [~] **R7.4** Rollout follow-up: progress, success, and failure detection (image pull errors, crashing) with the reason. No undo: a failed deploy is fixed by deploying another branch (user, 2026-11-10).
- [~] **R7.5** Restart, replicas, port-forward, shell (exec in a terminal view), logs (multiple pods, level filter, a text filter, pause, follow, scrolling back as far as the cluster kept). No k9s: devdeck's own UI does it (user, 2026-11-10).
- [~] **R7.6** Protected envs (declared in config) refuse writes until unlocked by typing the env name.
- [~] **R7.7** Branch matrix: services × envs with the image tag in each cell; highlight a tag.
- [~] **R7.8** Works with what the user's access allows; missing permissions are explained, not hidden.

## 8. Lifecycle

- [~] **R8.1** Quitting with running processes (in any workspace) asks: "Stop all and quit" or "Cancel". Cancel keeps the app open. On macOS the Dock's Quit, logout and shutdown can't ask (GPUI has no hook before them): they stop everything and quit (`docs/PLATFORMS.md` L13).
- [~] **R8.2** Child processes never outlive the app unless the user chooses so (process groups are killed on quit). Exact on Linux (scopes); best effort on macOS, where a process that double-forks and leaves its session can escape (`docs/PLATFORMS.md` L2); and on macOS, until its step 1a, the Dock's Quit, logout and shutdown leave runs going (L13).

## 9. Look and themes

- [~] **R9.1** Dark, dense, flat look of the approved prototype: 24 px rows, hairline dividers, color only for state and always paired with an icon or a status dot.
- [ ] **R9.2** Themes are data files of color tokens. One theme ships for now: the prototype's dark theme with slightly more contrast.
- [~] **R9.3** A shared component library (rows, tabs, buttons, inputs, menus, badges, key hints, text view, terminal view…) is the only way views draw UI, for visual parity.

- [~] **R9.5** Buttons, marks and messages use real icons (one outline set, drawn in the theme's colors and sized by the UI scale), never font glyphs; status dots are drawn shapes (decided 2026-11-07).
- [~] **R9.4** A Settings button in the title bar opens settings as a full-window view (not a tab). It holds global, per-machine choices: UI scale (for example 90–150 %, on top of the desktop's own scaling) and theme, and later more. Every size in the UI derives from the UI scale. Settings are saved to the config folder and apply immediately.
- [~] **R9.6** A scroll gesture moves one axis, the one it starts on, even in an area that scrolls both ways, terminals included (decided 2026-11-08, user: a sideways swipe on a long line also scrolled down). A sideways-only area scrolls with a sideways gesture or shift+wheel. Trackpads on Wayland; X11 reports every scroll as wheel notches, which GPUI doesn't lock.
- [~] **R9.7** The title bar shows the app's icon, not its name, which read as a menu (decided 2026-11-08, user). The name is the icon's tooltip and stays in window titles.
- [~] **R9.8** The main window reopens as it closed: maximized, or windowed at its last size (decided 2026-11-08, user).
- [~] **R9.9** Toolbars (user, 2026-11-10): every view's toolbar is built with one shared component and follows one rule. Its items (fields, actions, toggles, menu buttons, statuses, short texts) are each a registered action (R5.1) reachable by a key (never shown, R5.4), named in their tooltip, or saying why they can't be used (R5.5). It picks its form from the width it has, without lag: wide (icons and labels) when all fits; compact (icons only, but values and labels an item can't do without kept); narrow (items fold into a "more" menu at its end, in their fold order: 1 first); at the extreme the field truncates, then becomes a button. An item showing a state other than its default (a filter, pause) never folds; nor does a safety value (an env, its color with its icon). "More", reachable by mouse and keyboard, also holds what the view puts there and its figures. No view name (the tab says it; the sidebar's header is the exception), one line, never wraps (R4.4), one look and height for every item, no icon meaning two things. Logs is first; the others follow one at a time.
- [~] **R9.10** Nothing changes size or moves on the go (user, 2026-11-10): not when the pointer is on it, nor when it is selected, focused, pressed, dragged over or toggled. A menu, a popup, a row or a button keeps the size it was first drawn with. What a state shows is drawn over (a line, a color), never added beside: no text, icon or border appears, and no empty room is kept for one, except a toggle's check, whose room is kept whether on or off (a menu row's, the settings button's). Only a change in the data shown may resize something.

## 10. Configuration and setup

- [~] **R10.1** All configuration in `~/.config/devdeck/` (TOML): workspaces, folders, envs, clusters, tools, overrides, themes. State (pins, layouts, history) in `~/.local/state/devdeck/`. What the user writes in devdeck (notes, R12.3) in `~/.local/share/devdeck/` (decided 2026-11-08). On macOS: config in the same place; state and notes in `~/Library/Application Support/devdeck/state/` and `notes/` (decided 2026-11-10, `docs/PLATFORMS.md` §5).
- [ ] **R10.2** `SETUP.md` written for Claude: it walks a new user through an interactive setup on their machine (find project folders, detect tools and kubeconfigs, propose and write the config).
- [ ] **R10.3** Documentation where it is needed: architecture, adding a view, adding an action, components, config reference, themes.

## 11. Engineering

- [~] **R11.1** Work proceeds in steps: plan, review the plan with a subagent, assess, build, check visually across states, run tests, commit.
- [~] **R11.2** Unit tests for every feature; the whole suite runs before every commit so nothing regresses.
- [~] **R11.3** Dependencies are chosen deliberately (modern, fast, maintained) and pinned.
- [~] **R11.4** Performance is measured at every milestone, not assumed: memory at idle and under load, CPU at idle and under load, input latency, binary size, and a leak test (repeated open/close cycles must plateau). Results go in `docs/perf/<milestone>.md` and regressions are fixed before the milestone closes.
- [~] **R11.5** Development stops at the end of every milestone for the user's manual test.
- [ ] **R11.6** OS-specific code lives in one crate, `devdeck-sys`, behind an OS-neutral API, one backend per OS chosen by the build target, as `docs/PLATFORMS.md` §4 describes. Every feature that touches the OS goes through it, with a Linux backend, a macOS backend, or an explicit "unsupported" with its reason; an unsupported action is shown disabled with that reason. Until the crate exists, a step that adds OS-specific code adds it to the inventory in `docs/PLATFORMS.md`.

## 12. Files and notes

Files are view only; notes are the one thing devdeck edits (decided 2026-11-08, user).

- [x] **R12.1** A file view (`file/<path>`): any text file, view only, highlighted by its language (from the extension, plain text otherwise), line numbers, select and copy, find. Up to 10 MB; over 1 MB or with a line of 5 000 characters or more it shows as plain text, and says so. Not text (a NUL byte, not UTF-8) or bigger: a message names why. It follows the file while shown: changed on disk, it reloads keeping its scroll; deleted, it says so and keeps the tab; back, it shows it again.
- [~] **R12.2** A file dropped from outside (a file manager) onto a pane opens there: in the pane, or at an edge to split it, like a list row (R3.4); one already open moves there. Several files open one tab each, in the same place. A folder or a path that isn't UTF-8 is refused with a toast naming it.
- [x] **R12.3** Notes: Markdown notes belonging to an app, or to no project (a todo list), per workspace, kept in devdeck's data folder (R10.1), never in the project. Made, opened, renamed and deleted (confirmed) from the app's view, listed there alphabetically, and from the sidebar's Notes list (`ctrl+6`, after Terminals; user, 2026-11-09): Pinned + All, All a tree of one level of projects (nested ones too, by their app's name), each holding its notes, then the notes without a project; projects without notes don't show. "New note" there (a button, the All header's menu, `n`) makes one without a project, a project's menu one for it. A note never moves to another project. A note is saved by itself while it's edited (no save key, no unsaved marker) and whenever devdeck saves its state or quits. An app that goes away keeps its notes, listed under its id, dimmed, "project not found" on hover.
- [x] **R12.4** A Markdown file or a note shows its source or rendered, switched by an icon in its header (or tab strip), its tab menu, the palette and a key. A note opens rendered when it has text, as source when empty. What's shown is remembered per tab.

## 13. Control API

A generic API for everything devdeck shows and does; MCP and a CLI are its clients, and MCP can be replaced without touching the app (decided 2026-11-08, user). Plan: `plans/control-api.md`.

- [~] **R13.1** Everything a user can see or do in devdeck can be read or done through a local API, by explicit ids (never "what has focus"), under the same rules as the UI. Each operation is one function, called by the UI and by the API. No method runs an action by its id, presses a confirm, or drives a modal or a menu.
- [~] **R13.2** The API knows nothing of agents or MCP. It publishes its own catalog (methods, argument and result schemas, class, level). It only grows: an integer level, nothing removed or changed incompatibly; new methods may be marked experimental.
- [~] **R13.3** JSON-RPC 2.0, one message per line, on a Unix socket in `$XDG_RUNTIME_DIR/devdeck/` (on macOS, `~/Library/Application Support/devdeck/run/`, or `/tmp/devdeck-<uid>/` when the socket's path would pass 103 bytes: `docs/PLATFORMS.md` §5) (folder 0700, socket 0600), the caller's user checked; never an abstract socket, never a network port.
- [~] **R13.4** A caller is known from its process tree, never from a token: a process descending from a shell devdeck started is that terminal. Anything else is outside and may only look, unless the user raises that one program with a card, while it runs. Shells get the socket's path and their terminal in their environment, which grant nothing; app runs get neither; devdeck removes them from its own environment at start. A terminal's grants end with its shell.
- [~] **R13.5** Every call has a class, from the method and what it acts on: observe, read, present, organize, run, type, remote, destructive. A caller's policy says allow, ask or deny per class (presets: observer, viewer, operator, full). Acting on what the user or another caller started asks; on what the caller started follows its class. Checks, all needed, in order: the policy, the scope (the caller's workspace; protected envs excluded by default), devdeck's own rules (edit mode, protected env, main/master never pushed), approval, rate limit, audit. Defaults for a terminal: the table in the plan.
- [ ] **R13.6** Every confirmation goes through one approvals service; modals are one way to show it. Functions that destroy require a proof that only the user's answer in the UI makes. An approval is used once, expires in seconds, and is bound to the caller, the method, the exact arguments and the state it was decided on; a change in that state refuses the call. Its card: in an area nothing else draws in, names the caller, shows the arguments in full (wrapped, control and right-to-left characters escaped), never takes focus, Allow is never Enter or y; answers once, for this terminal for some minutes (not for typing into another's terminal, nor protected envs), or deny.
- [~] **R13.7** Never through the API: turning edit mode on, unlocking a protected env (unlocks are per caller), changing permissions, reading or clearing the audit, answering approvals. Typing into the caller's own shell is refused.
- [~] **R13.8** Every call that changes something is audited (time, caller, process, method, arguments, decision, result). An API access panel lists the callers, their permissions (changed only there) and the audit.
- [~] **R13.9** Reading text is bounded (limit, tail, a cursor for what's new, search with context, a truncated flag), plain by default or as the screen shows it. Free text is marked untrusted, secrets devdeck knows of are hidden, and what a client reads never changes what it may do. Files are read only inside the workspace's folders.
- [~] **R13.10** Long operations, approvals and waits are jobs; a wait that times out returns the state and the output so far. Events by subscription, numbered, with a bounded queue per client (overflow: `lagged`, then the client reads again). Nothing runs while no client asks for it (R1.3).
- [~] **R13.11** Clients depend only on the API's crate: `devdeck-ctl` (CLI) and `devdeck-mcp` (MCP over stdio). The MCP server offers a few chosen tools plus one per class, hints from the class, only what the caller may use; a call needing approval answers at once with a job.
