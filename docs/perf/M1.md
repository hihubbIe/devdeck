# M1 performance

Measured 2026-11-07 with `scripts/measure.py` on the release build (thin LTO,
stripped), same machine and session as [M0](M0.md) (Wayland, GNOME 50.1, AMD 880M,
Vulkan). Every scenario ran with fresh temporary `DEVDECK_STATE_DIR` and
`DEVDECK_CONFIG_DIR`: the default layout of the `work` workspace, 100 % UI scale, the
sidebar showing Apps, the demo log stream in the focused pane. The fake runner starts
three servers (two in `work`, one in `personal`) that each write a line every 2 s.

## What changed while measuring

The first M1 run showed regressions: idle CPU 0.60 % with 20 renders in 20 s, and streaming 12.3 %. Three fixes:

- **Run output stopped redrawing the window.** Each output line of a background server notified the runner. The notification went on to the services, the sidebar and the window, so the whole window redrew every 2 s per server, even with nothing on screen showing that run. Lines are now events that only an open run view listens to; state changes still notify. Idle: 0.60 → 0.10 %, renders 20 → 0.
- **The hint bar is cached per focus.** It walks the action registry, about 130 entries, and it did so on every frame of a streaming view.
- **The sidebar and pane views are cached GPUI views.** They are redrawn only when they change; theme and scale changes refresh everything. Streaming: 12.0 → 9.9 %. With the sidebar hidden it was 9.5 % before caching, so the cost of the sidebar is now small.

## Leak run

A cycle does one of everything (`crates/devdeck-app/src/stress.rs`):
- opens each view type (app, run, service, service logs, matrix, port, a demo view) and presses Esc in the service view's tag editor;
- starts and stops a run;
- splits, collapses, maximizes and detaches a tab, opens a menu in its OS window, and re-attaches it;
- opens the palette, the cheat sheet and a menu;
- switches the workspace and the named layout away and back;
- closes it all.

So a short run covers every path. M0's cycle did much less, so its 89 B per cycle doesn't compare directly.

**Heap, by source line** (`scripts/measure.py heapdiff`: heaptrack on 10 and 30 cycles, teardown skipped, diffed; about 40 s):

| per cycle | where | verdict |
|---|---|---|
| about 400 B | GPUI's Wayland window objects, `gpui-pre-linux` `wayland/window.rs:864`, one window opened and closed per cycle | GPUI; matters only when windows open and close; to report upstream |
| 63 B | run output buffer, `runner.rs` | capped at 5 000 lines per run |
| a few hundred B, varying between runs | hash map capacity, frame buffers | noise: changes sign between runs |

**Private memory** (300 cycles):

| cycle | RSS | PSS | private |
|---|---|---|---|
| 0 | 114.0 MB | 55.7 MB | 49.8 MB |
| 100 | 120.3 MB | 62.0 MB | 56.0 MB |
| 200 | 120.5 MB | 62.2 MB | 56.2 MB |
| 300 | 120.6 MB | 62.2 MB | 56.3 MB |

From cycle 200 to 300 that's 0.96 KB per cycle, falling, against about 460 B of live heap; the difference is the allocator and the Vulkan driver settling. Every checkpoint showed 0 leaked views, one overlay layer, no metrics sampler left, and the window count back to 1.

**Found and fixed by profiling** (details in the step 7b sections of `docs/plans/M1-prototype.md`):
- The demo log stream kept streaming behind other tabs.
- The leak check's own list of closed views grew forever in normal use.
- The earlier idle and streaming regressions.

## CPU while streaming (perf)

`perf record --call-graph dwarf` during the stream. The time is GPUI's frame work:
- shaping the new log lines (`cosmic_text`, bidi, `harfrust`): about 13 %;
- painting glyphs: about 8 %;
- `memmove`: 6 %;
- allocation, `taffy` layout and the hit-test tree: the rest.

No devdeck function is among the top entries. Shaping new lines every frame is inherent to a 2 000-line/s stream. If it matters later (M2's real terminal grid), it gets a cache at the line level.

## Not measured in M1

- **Latency.** The scenario types real keys with `xdotool`. During M0 that sent a stray key to another focused window on this desktop, so it isn't run unattended. M1 adds no work on the key path beyond the registry lookups GPUI already does. A new measurement needs the user present, or a nested X server (none is installed).
- **Cluster feed.** No cluster settings were in the environment. M1 didn't change the M0 feed.
