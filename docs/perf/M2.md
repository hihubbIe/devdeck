# M2 performance

## Terminal trial (step 1, 2026-11-07)

Release build, Wayland, same machine as [M1](M1.md). `scripts/measure.py terminal`: the
demo's three fake servers write 2 000 lines/s each through the run engine and their
terminals (`alacritty_terminal`); one is shown in a run view. Fresh state and config.

| measure | value |
|---|---|
| CPU, three runs at 2 000 lines/s, one shown | 18.0 % |
| CPU, the same three runs, none shown (the demo log list shown instead) | 12.75 % |
| CPU, M1's scenario (demo log list at 2 000 lines/s), same build | 9.4 % (M1: 9.6 %) |
| memory of three full terminals (5 000 lines of history, ~120 columns) | 37 MB USS, ~12 MB each |

- Parsing is cheap: about 1 % per run at 2 000 lines/s in the background. perf puts
  `alacritty_terminal` at 1.3 % of samples and building rows at 1.2 %.
- Drawing a terminal on screen costs about 14.7 %, against 9.4 % for M1's line list: GPUI
  frame work (layout, hit-test tree, text shaping) for every output frame. To work on in
  step 2 (builder F), for example by redrawing only rows that changed.
- About 3 % is the fake driver's own string formatting, which real processes don't have.
- Verdict: go. History is capped at 2 000 lines per run (about 5 MB when full; memory
  only grows as a run writes).

## Terminal drawing (step 2, builder F, 2026-11-07)

Same scenario (`scripts/measure.py terminal`), release build.

| CPU, three runs at 2 000 lines/s, one shown | |
|---|---|
| before (re-measured) | 20.4 % (18.0 % in the trial) |
| one canvas draws the visible rows (no layout box per row) | 15.9 % |
| plus streaming redraws coalesced to 30 fps (immediate within 500 ms of typing) | 11.2 % / 10.9 % |
| M1's line list, for comparison | 9.4 % |

perf put the remaining cost in shaping rows that are new every frame (inherent at this
rate), painting glyphs, and the window-wide layout `WindowView` redoes when a view is
notified. Memory is unchanged (about 14 MB for the history of three full runs).
