# M2 performance

## Terminal trial (step 1, 2026-11-07)

Release build, Wayland, same machine as [M1](M1.md). `scripts/measure.py terminal`: the
demo's three fake servers write 2 000 lines/s each through the run engine and their
terminals (`alacritty_terminal`); one is shown in a run view. Fresh state and config.

| measure | value |
|---|---|
| CPU, three runs at 2 000 lines/s, one shown | 18.0 % |
| CPU, the same three runs, none shown (the demo log list shown instead) | 12.75 % |
| CPU, M1's scenario (demo log list at 2 000 lines/s), same build | 9.4 % (M1: 9.6 %) |
| memory of three full terminals (5 000 lines of history, ~120 columns) | 37 MB USS, ~12 MB each |

- Parsing is cheap: about 1 % per run at 2 000 lines/s in the background. perf puts
  `alacritty_terminal` at 1.3 % of samples and building rows at 1.2 %.
- Drawing a terminal on screen costs about 14.7 %, against 9.4 % for M1's line list: GPUI
  frame work (layout, hit-test tree, text shaping) for every output frame. To work on in
  step 2 (builder F), for example by redrawing only rows that changed.
- About 3 % is the fake driver's own string formatting, which real processes don't have.
- Verdict: go. History is capped at 2 000 lines per run (about 5 MB when full; memory
  only grows as a run writes).

## Close (step 5, 2026-11-07)

Measured with `scripts/measure.py` on the release build (thin LTO, stripped) of commit
`6d62a92` plus uncommitted test-only changes, same machine and session as [M1](M1.md)
(Wayland, GNOME, AMD 880M, Vulkan). Every scenario ran with fresh temporary
`DEVDECK_STATE_DIR` and `DEVDECK_CONFIG_DIR`. The user's own devdeck (default state
folder) ran on the same desktop throughout. MB here is 1 024 kB as `/proc` reports them;
M0 and M1 don't say which unit they used.

Two new scenarios use real processes instead of the demo's fake driver:
- `real`: a config folder with one workspace whose folder holds one project, `stream`,
  whose Makefile's `run` is a python script writing 2 000 lines/s with ANSI colours
  (about 75 characters, five styled spans each). The state folder says its run view was
  open with the run running, so it starts again at launch (no app hook needed); the view
  is opened with `DEVDECK_OPEN`. One run, against the demo scenario's three.
- `leftovers`: the same project, its recipe `setsid sleep 30101 & sleep 30102 & python3
  stream.py 20 …`: a child that leaves the process group and session, an ordinary child,
  and a slow stream. Three devdecks on the same folders: SIGTERM, kill -9, then the next
  start (the run was running, so it starts again) and its SIGTERM.

### Leak run

1 000 cycles (`scripts/measure.py leak`):

| cycle | RSS | PSS | private |
|---|---|---|---|
| 0 | 118.6 MB | 77.2 MB | 48.1 MB |
| 250 | 134.0 MB | 92.9 MB | 63.6 MB |
| 500 | 134.1 MB | 93.0 MB | 63.7 MB |
| 750 | 134.2 MB | 93.1 MB | 63.8 MB |
| 1 000 | 134.3 MB | 93.2 MB | 63.8 MB |

Private memory per cycle: 573 B (250 → 500), 360 B (500 → 750), 311 B (750 → 1 000).
Still growing past 500, so `heapdiff` ran on the build with symbols:
- 196 B per cycle under `deck.rs:679` (`cx.open_window` for the detached tab's OS window,
  reached from `deck.rs:559`): GPUI's window objects, one window opened and closed per
  cycle. The same item as M1's (about 400 B there).
- 177 B with no devdeck frame. A second heaptrack pair, read by hand, split this kind of
  growth into `libwayland-client` proxies (`wl_proxy_marshal_array_flags`, two per
  cycle), a GPUI element-state hash map resizing once, and calloop's poll-event vector:
  GPUI and Wayland again, and capacity that changes between runs.
- the rest under 40 B per cycle, GPUI or `wgpu` (atlas command buffers).

No devdeck structure grows per cycle. The private growth after warm-up (336 B) is below
the live heap growth (455 B), so the heap explains it; it falls with every quarter. Like
M1, it's above the 200 B threshold because a detached OS window opens and closes every
cycle; it matters only when windows open and close (to report to GPUI upstream).

The cycle doesn't exercise M2's newer features: its menus open with no items
(`stress.rs` 219 and 237), so no submenu; it opens no terminal tab (`term/…`), and its
run goes through the demo's fake driver, not a pseudo-terminal. Whether the views it
opens draw the new icons wasn't checked. Extending it isn't trivial (a terminal tab
needs a real shell), so it wasn't extended.

The warm-up grew private memory by 15.5 MB in the first 250 cycles (M1: 6.2 MB in the
first 100). It isn't attributed: the heap diff starts at cycle 10.

### Notes

- **PSS at start is 22 MB above M1's, USS is 1.3 MB below.** In a devdeck started on
  its own, `libLLVM.so.21.1` had 46 MB of pages shared with other processes, counted as
  25 MB of PSS; it comes with Mesa's Vulkan drivers (`libvulkan_lvp`, `libgallium`), which
  the Vulkan loader maps. PSS depends on how many other processes touch the same pages,
  so this is the desktop, not devdeck. USS, devdeck's own memory, is flat.
- **A real run against the demo.** One real run at 2 000 lines/s, shown, costs 11.9 to
  12.3 %, against 11.07 % for the demo's three runs with one shown. perf of the real run
  shows GPUI's frame work at the top, as in step 2: `memmove` 3.4 %, `paint_glyph` 2.9 %,
  `cosmic_text` shaping 2.9 %, `harfrust` 2.2 %, `taffy` 2.2 %, script lookup 2.1 %,
  `AttrsList::get_span` 2.0 %, `paint_line` 1.8 %, the hit-test tree 1.8 %,
  `Terminal::row` 1.6 %. The real lines carry five styled spans each and the demo's
  don't, and shaping works span by span; that this explains the difference wasn't
  measured (no run with plain lines). The stream kept 2 000 lines/s: devdeck never held
  it back. One full real run's history takes 6.4 to 7.1 MB, against about 4.5 MB for
  each demo run (13.6 MB for three); not attributed.
- **SIGTERM (R8.2).** devdeck exited in 0.02 s. The group leader, the ordinary child,
  the stream and the child that left the session were all gone; the group log was empty.
- **Fixed since** (a systemd scope per run, see the plan): `scripts/measure.py
  leftovers` again, with the daemon now double-forked (out of the run's tree at once).
  SIGTERM: devdeck exited in 0.03 s and left nothing. kill -9: only the daemon
  (`sleep 30101`) survived, its scope recorded with a devdeck that's gone; the next
  start offered it (1 scope); that devdeck's own SIGTERM left it alone (only the user
  decides), and the script killed it. The finding as first measured:
- **kill -9 (R8.2): the child that left the session survives and is never offered.**
  After kill -9, the pseudo-terminal closed and the kernel hung up the run's session:
  the leader (`sh -c make run`), the ordinary child and the stream ended. `setsid sleep`
  survived, as expected. But the group log records only the group leader
  (`process.rs:281`, `log.add(self.pid, self.start)`), and `GroupLog::leftovers`
  offers only recorded pids that still run (`process.rs:531`). The leader had ended, so
  the next devdeck offered nothing, pruned the entry when its own run started
  (`process.rs:558`), and its SIGTERM didn't kill the survivor either; the scenario
  killed it. Checked through the state folder's `processes` file and `/proc`; the
  dialog itself wasn't seen, since nothing was offered. `tests/lifecycle.rs` covers only
  a recorded pid that still runs (offered, killed on Kill, kept on Leave), not a
  descendant whose leader ended. A run whose leader ignores SIGHUP would leave its
  leader running and get the offer; not tried in the app.
  Possible fix: record the processes that leave the group in the log too (the run's
  thread already finds them with `Tree::collect`; doing it periodically while the run
  runs and writing `pid start leader` lines), and have `leftovers` and `kill` count a
  group as left over while any recorded member still runs.
- **Latency.** Not measured: the session is Wayland, no X11 server other than Xwayland
  and no nested one (Xvfb, Xephyr) is installed, and in M0 `xdotool` sent a stray key to
  another window on this desktop, so it isn't run unattended.
- **Cluster feed.** Not measured: no cluster settings in the environment.
